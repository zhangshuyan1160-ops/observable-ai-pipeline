## 目标与验收底线

评审应能在五分钟内看到：提交动画任务 → 查看每个步骤 → 某步骤失败并重试 → Worker 中断后恢复 → 相同输入再次提交命中缓存 → 查询历次尝试和产物。计算过程可 mock，任务状态与恢复机制必须真实持久化。

主交付选择公开 GitHub 源码仓库，满足题目“公网 URL 或公开 GitHub”二选一要求。代码之外提供中文 Markdown 简要说明、运行步骤、测试证据和演示截图。公网运行 URL 为附加项，不占用故障验证时间。

**工时为 AI 辅助下的工程投入估算，不是已发生的个人工时，也不是完成承诺。** 核心工作约 18 小时，预留 4 小时缓冲，共 18–22 小时；两天各需约 9–11 小时可用时间。实际可投入时间不足时，按下方裁剪，不压缩核心恢复验证。

## 技术决策

| 选择 | 原因 | 代价 |
| --- | --- | --- |
| FastAPI + Python | 接口与 mock AI 步骤共用语言，已有技能可复用 | 计算进程必须与请求服务分离 |
| PostgreSQL 同时存状态和就绪队列 | 单事务解决状态/入队双写；可直接演示领取与 fencing | 适合低吞吐 MVP；不是通用调度平台 |
| 少量独立 Worker | 能真实杀进程并恢复；CPU/GPU 路由清晰 | 不实现弹性伸缩、节点发现或 HA |
| 本地持久化产物卷 | 复用和校验直观，部署简单 | 多机需对象存储，磁盘损坏不在恢复承诺内 |
| 原生 HTML/CSS/JS + 1–2 秒轮询 | 不增加前端构建与实时连接维护成本 | 大规模高频更新后需增量推送 |
| 固定 DAG 与 mock 计算 | 展示依赖、扇出合并、检查点即可 | 不实现可视化拖拽编排和真实模型 |

Temporal、DBOS、Celery 均是有效候选。此题优先展示执行语义及其测试，选择一个范围明确的数据库执行器；生产级跨机耐久执行应重新评估成熟框架。不能把这个选择说成自研总是优于框架。
