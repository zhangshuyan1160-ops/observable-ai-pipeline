# 人工开发与复核清单

以下是建议本人实际完成的工作，不是已经完成的经历。预计 45–75 分钟，只是练习预算；完成后记录真实起止时间、改动和证据，再更新提交说明第 6 节。

## 1. 亲自复现恢复（约 15 分钟）

按 README 启动服务，新建 32 帧、每批 4 秒、关闭缓存的任务。看到风格化至少保存 4 帧后，在终端执行：

```bash
.venv/bin/python scripts/dev.py interrupt gpu
```

记下 task ID、保存帧数、旧/新 Worker、两次 attempt 状态和恢复起点。检查 probe/extract 没有新增尝试。再运行一次“首次失败”和一次“本轮全部失败，手动恢复”，解释自动重试和手动重试轮次的区别。

验收：本人能解释为什么杀进程后不会立即重领、为什么旧 Worker 不能覆盖新结果、哪一批可能重算。

## 2. 亲手实现一个小功能（约 20–35 分钟）

建议在任务列表中加“按任务名称筛选”。仅修改 `src/pipeline/web/app.js` 与必要 CSS，限定在最近 30 条已加载任务上筛选，不改执行器状态或数据库。

需求：输入关键词后列表匹配名称；清空恢复原列表；无匹配时显示明确提示；当前任务详情保持可查看；大小写不敏感。不要把客户端最近任务筛选称作全量数据库搜索。

本人阅读 renderList、输入事件绑定和样式后自行实现；本清单不给出完整代码答案。用 Git diff 查看自己的改动，刷新浏览器验证五种行为，保存一次清晰的提交。

验收：本人能说明改了哪几处、为什么选择前端筛选、如果超过 30 条应怎样扩展 API。

## 3. 核查与讲解（约 10–25 分钟）

- 阅读 engine.py 的 claim、owned、complete、reap 和 retry，画出“领取→执行→提交/回收”的事务边界。
- 用相同输入创建新任务看 CACHED，再改模型版本看失效边界。
- 运行 pytest，确认实际结果；依据 failure-matrix 区分已测行为和扩展设计。
- 讲解真实 GPU 为什么不能仅凭租约超时就认定显存释放。
