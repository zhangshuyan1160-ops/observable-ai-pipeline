# 题 D：可观测 AI 任务管线 MVP 提交说明

交付工程：**Frameflow / observable-ai-pipeline**。运行入口与测试命令见 [README](../README.md)。公开源码：[GitHub 仓库](https://github.com/zhangshuyan1160-ops/observable-ai-pipeline)。本地演示不依赖租赁服务器。

## 1. 实现方式与时间规划

采用 Python 3.12、FastAPI、PostgreSQL、独立 CPU/GPU mock Workers、原生 HTML/CSS/JS。数据库兼作持久状态与就绪队列，避免队列/数据库双写。实际生成小 GIF、PNG、ZIP，AI 推理耗时与 GPU 遥测模拟。

按两天规划：D1 完成调研、持久化与执行/恢复闭环约 9 小时；D2 完成缓存、检查点、界面、故障验证与交付约 9 小时，另留 4 小时缓冲。以上为工程预算，实际工时以活动记录为准。为保留恢复验证，裁掉任意 DAG 编辑、真实模型、SSE 和公网部署；原生 PostgreSQL 避免安装 Docker Desktop。详见 [计划](plan.md)。

## 2. 长任务、状态管理与恢复

HTTP 创建立即返回 202，任务不依赖请求连接或 API 存活。任务有 QUEUED/RUNNING/CANCELLING/CANCELLED/SUCCEEDED/FAILED；步骤区分依赖等待、资源等待、运行、重试等待、成功、缓存、失败与阻塞；每次 attempt 独立留史。

10 秒租约、2 秒心跳发现失联；可重试错误默认每轮最多 3 次，指数退避加抖动；永久错误早停。手动重试新建轮次，保留成功上游与旧历史。fencing token、当前 attempt 和数据库 deadline 共同校验迟到写入。语义是至少一次计算，不承诺 exactly-once。风格化每 4 帧保存检查点，恢复仅重做未提交批次。

小时级扩展需区分排队/执行/心跳/进度超时，使用对象存储和分块产物、资源配额、容器退出确认、版本兼容与事件保留策略；外部 AI 调用要持久化 provider job ID 防止重复付费。新增真实数据库停机和全栈重启演练；单任务小时级演练已通过，实际运行 3607.93 秒，期间两次故障后分别从 4/8 帧继续；这不等同于吞吐压力测试。

## 3. 步骤与依赖

固定 DAG：probe→extract→stylize→compose→package，另有 extract→thumbnail→package。创建时验证无环并保存定义/参数快照，父步骤全部成功或缓存后领取。extract 在本例生成帧索引，stylize 才生成 PNG。风格化是昂贵独立批次，适合检查点；缩略图可与其并行；有编码器内部状态的合成按整步重做更简单。每个张量算子无需独立持久化。

## 4. 持久化内容与原因

持久化 tasks、steps、attempts、events、artifacts、cache_entries、workers、resource_slots。分别支撑恢复决策、尝试审计、增量查询、摘要校验、结果复用和资源所有权。状态和事件同事务；事件序号在任务行锁内分配，避免分页漏掉晚提交事件。文件先原子写入，后带 fencing 登记；数据库未提交的孤儿文件不视为成功。

缓存指纹覆盖步骤/处理版本、相关参数和父产物摘要；模型/seed 变化使风格化及下游重算，上游仍可复用。只复用成功且摘要/大小通过校验的产物。定义快照已存，但数据库 v1→v2 迁移已实现；工作流定义和检查点跨版本热迁移尚未实现。

## 5. AI coding 工具、Token 与主要消耗

使用 Codex 桌面版辅助开发，并用 Skills CLI 完成 12 组 find-skills 搜索、232 个去重候选筛选，新增 6 项固定版本技能，详见 [技能清单](skills.md)。辅助范围包括方案梳理、实现、测试、页面与文档；未使用子代理，模型具体版本未独立核验。

截至 2026-10-12 16:58:55 的当前会话累计约 **2764.9 万 tokens**，其中缓存输入约 **2648.6 万**、输出约 **18.6 万**；未缓存输入加输出 **1,162,389**。缓存输入已包含在总输入中，不能重复加总，也不能直接视为费用或新生成代码量。相较上一交付快照，本轮优化、验证、等待与状态交流累计增加约 1841.1 万，为已记录阶段中的最大增量；缺少模块级计量，不能给出函数或页面的精确比例。大量重复上下文及工具说明计入输入。此为阶段快照，后续发布另计，见 [本轮用量快照](evidence/ai-usage-v0.2.json)。

## 6. 个人时间最多的部分

人工环节优先安排在恢复机制的理解与故障复现，其次是小功能修改、代码核查和演示讲解。具体操作与验收标准见 [人工开发与复核清单](manual-validation.md)。个人最耗时环节及实际分钟数将在完成这些操作后补充；AI 生成和等待时间单独计算。

## 7. 失败案例与能力边界

当前 31 项测试在本地、独立安装环境和 Linux CI 均通过，覆盖队列饥饿、取消竞态、历史查询和迁移，以及真实 PostgreSQL 并发、超时、缓存损坏与 Worker SIGKILL；真实 HTTP 演示同时重启 API/Worker，4 帧检查点由新尝试接续，成功上游不重算，下载摘要一致。详见 [验收矩阵](failure-matrix.md)。

实际开发问题：测试辅助函数误以为全局 CPU 队列两次领取必然推进指定任务，修成状态条件等待；页面切换终态步骤会清空时间线，修成保留并重绘事件数据。首次 Linux CI 还发现测试依赖本地启动器已创建的临时父目录，修成测试初始化时自行创建。它们与故障注入案例分开记录。

GPU 为 8GiB 单槽模拟，显示占用/排队/Worker 心跳，超容量拒绝且退避释放槽；真实 GPU 需节点代理确认旧进程退出、DCGM 指标和 OOM 分类。fencing 无法停止失联进程。已补充真实数据库停机/恢复、完整服务重启、任务取消和历史管理；尚未完成多机调度、鉴权、自动孤儿文件 GC、真 GPU 与高并发压力测试；Compose 仅提供配置，未运行验证。两天 MVP 选择把证据集中在单机恢复语义上。

本轮实际发现并修复了“先截取 32 个活跃任务再筛资源”导致队列饥饿的问题，修改前两条回归测试失败、修改后通过。取消需等待线程内操作结束才能确认停止；此边界也有专项测试。详见 [v0.2 四项优化](priority-one.md)。
